# P5.3 部署一致性排查（robust_d it12000，冻结；未训练、未改 Policy/控制律）

数据：P5.2 完整舞蹈三次实机日志（`logs.zip`：run1 `180154` 操作员 START×2 退出 / run2 `180218` COMPLETED / run3 `180317` UNSTABLE 退出，0.92 s）。
脚本与结果：`results/p5/analysis/`（`p53_consistency_audit.py`、`p53_sim2sim.py`、`p53_guard_ablation.py`、`p53_cmd_replay.py`、`p53_figures.py` 及 `*.json/*.png`）。

## 结论（先看这里）
1. **超过 95% 的指令裁剪不是“部署端把动作截坏了”那么简单：根因是 Policy 本身大量输出超出硬限位的关节目标**，主要是**踝 pitch**（动作均值 +2.2~+2.8，目标 +0.7~+2.0 rad，硬限位 +0.52）。训练仿真里同一个 Policy 也是这样：robust_d 原生评测 **56%** 的 tick 有原始目标越限。
2. 但**部署端有一处确定的实现偏差把它放大了**：训练的执行器对目标**不做限位**，只在力矩上饱和（mjlab `BuiltinPositionActuator` + `actfrcrange`，踝 50 Nm）。部署的安全门把目标裁到限位内，于是驱动器收到的是 `kp·(限位−q)`，**不是饱和力矩**。三次实机里踝 pitch 实际力矩比训练等效力矩**平均少 8.7–14.1 Nm（最大 46 Nm，38–59% 的 tick 少 >5 Nm）**；run3 失稳前 0.7–0.85 s 左踝目标跳到 +1.97 rad，训练里会给 50 Nm，实机只送出约 13 Nm，随后倾角增长（0.92 s 触发 UNSTABLE，退出过程中峰值 0.51 rad）。实测力矩 `tau_est` 紧跟被裁剪后的指令（图 `fig_run3_left_ankle.png`）——驱动器是在“忠实执行被削弱的指令”。
3. 在 MuJoCo Sim2Sim 里只改这一点（72×2 次随机化运行/条件，真机初态）：**训练语义**（不裁目标）原始目标越限 54–60%、跟踪 rms 0.048；**部署安全门**越限 **86–92%**、rms 0.064–0.070、最大倾角 0.15→0.17（max 0.29）。真机实测越限 89%/96%/99%，**与“部署安全门”仿真一致，与训练一致的 56% 不一致**——Policy 在拿不到预期力矩时输出更大的踝动作（闭环加剧）。
4. **仿真没有复现跌倒**（144 次全部不倒、倾角 <0.4），所以“安全门裁剪”解释了裁剪率和动作还原度下降，**不能单独证明它导致了 run3 的失稳**；真机踝（并联连杆，`tau_est` 最高 77 Nm 而指令 ≤46 Nm）与仿真执行器的差异仍是未排除的第二因素。这属于 **Policy 对踝力矩饱和的依赖（泛化/鲁棒性问题）**：它把踝当成力矩饱和的 bang-bang 平衡器，真机踝只要有一点力矩偏差就失稳。
5. **次要偏差**（已查明）：(a) 训练片段 `ssb_padded` 在舞蹈前有 **50 帧（1 s）冻结首帧**，部署的 `motion.bin` 没有，舞蹈一开始就走（Sim2Sim 影响很小：倾角 0.17→0.15，但仍是部署与训练的不一致）；(b) 髋 roll 力矩上限 **88 Nm（policy_params / sim2real cfg）vs 训练 139 Nm**（mjlab 电机）——真机 `tau_est` 已达 99 Nm，说明驱动器能超过 88；只影响约 7–13% 的 tick，缺口 ≤25 Nm，**未改**（硬件限值只收紧不放宽，需你按硬件规格确认后再动）。
6. **没有发现的问题**：关节顺序、默认姿态、action scale、kp/kd、关节位置限位、观测拼接与历史、参考帧切片、yaw 偏移均与训练一致（见下表）。

## P5.3 的改动（均已回归）
- **`lead_in_s 1.0`（默认，site.conf）**：`running` 模式在内存里补 50 帧冻结首帧，复现训练片段；`motion.bin` 与哈希不变；`run_s` 仍是舞蹈秒数。
- **`--torque-ff` / `guard_torque_ff 1`（默认关，实验）**：目标仍裁在限位内（硬件保护不变），把训练等效饱和力矩 `clamp(kp(q_policy−q)−kd·dq, ±effort)` 与实际 PD 力矩之差作为 `LowCmd.tau` 前馈发出（≤力矩上限；退出帧永不前馈）。自检 7j 验证“总力矩 = 训练力矩（1e-14）”。**未在真机验证**——它会让踝在限位处以最大 50 Nm 顶住限位，与训练一致但真机没试过；建议按 `exit` 之后的未验证授权单独 A/B（先 `clip2`）。日志新增 `tau_ff:*`、`tau_train:*` 列。
- 日志统计：新增 `tracking`（Policy 原始目标 / 裁剪后指令 / 实际位置 / 参考分开统计，裁剪分解，力矩缺口）和 `attitude_extremes`（修正：最大倾角含触发帧与退出过程，run3 由 0.26 → 0.51）；`guard_stats.max_tilt` 同步修正。
- Service：可恢复退出自动回 IDLE（见 README）；修复 guardian 正常退出 → 误报 CRITICAL → SIGTERM runner（现场日志 `18:02:09`/`18:02:41`/`18:03:27`）以及 START×2 后 runner 的 post-exit 记录被 2.5 s 升级计时误杀。

## 仍未解决 / 建议的下一步真机试验
1. **踝力矩 A/B**：`clip2`（含默认 1 s 前导）分别 `--torque-ff` 关/开各做一次，对比 `tracking.torque_vs_training`、越限比例、倾角（需要未验证授权，且每次吊带）。若 ff 开后稳定性显著改善，说明主因是部署执行器语义；若仍失稳，问题在真机踝动力学/Policy 对踝饱和的依赖，需要训练端处理（不属于本阶段）。
2. 真机踝（并联机构）的 `tau_est` 与指令力矩的关系（77 vs ≤46 Nm）需要硬件资料或专门的踝力矩阶跃标定。
3. 髋 roll 力矩上限 88 vs 139：按硬件规格确认后再放宽。
4. 足底穿透、动力学安全项仍 FAIL（未处理）。
